# FloatNote · 悬浮便签

一个常驻 Windows 桌面、始终置顶的小窗工具。用来临时收纳截图和关键信息，
避免在多个页面之间来回跳转丢失上下文。

---

## 一、最终方案：WPF + WindowChrome + DWM 原生合成

选择依据不是"哪个框架更时髦"，而是这个需求里三个硬约束的交叉点：

| 约束 | 含义 |
|---|---|
| 多开窗口 | 每多一个窗，边际开销必须接近零 |
| 始终置顶 | 窗口必须被 DWM 持续合成，无法靠"最小化"省资源 |
| 截图 + 图片 | 需要位图解码、缩放、虚拟化列表 |

### 为什么不选其他方案

| 方案 | 安装包 | 单窗基线(实测) | 多窗边际 | 判断 |
|---|---|---|---|---|
| Electron | ~80 MB | 150–300 MB | 每个窗口翻倍 | ✗ 一个便签吃掉半个浏览器 |
| Tauri (WebView2) | ~3 MB | 60–120 MB | 每窗一个渲染进程 | ✗ 多开即多进程 |
| **WPF (.NET 10)** | **282 KB** | **114 MB** | **≈0** | ✓ 采用 |
| WinForms | ~150 KB | 31 MB | 很低 | 备选，见下方权衡 |
| 纯 Win32 (C++) | ~50 KB | 5–10 MB | 极低 | 最省，但开发成本高 |

上表基线数据为实测值（测试机：Windows 11、16 逻辑核、3200×2000 @200% 缩放），不是引用资料。

## 二、让它真正"轻"的六个关键决策

### 1. 绝不用 `AllowsTransparency="True"` 做圆角

这是 WPF 悬浮窗最常见的性能陷阱。开启后窗口会被降级为 Layered Window，
**强制软件渲染**，拖拽时 CPU 可直接飙到 15% 以上。

正确做法：`WindowChrome` + `DwmExtendFrameIntoClientArea` 扩 1px 边框，
让 DWM 用 GPU 画圆角和投影。见 `Native.cs:EnableNativeFrame()`。

### 2. 不用 `DropShadowEffect` 做投影

WPF 的 `DropShadowEffect` 是软件渲染的，每个窗口都会持续占用 CPU 重算模糊。
改用 DWM 原生投影后，这部分开销归零，且投影质量更好。

### 3. 截图先限尺寸再解码

`Clipboard.GetImage()` 返回原分辨率位图。一张 4K 截图解码后约 33 MB。
用 `DecodePixelWidth = 1600` 延迟解码，单张降到 2–3 MB；缩略图再按 1400 宽解码。

### 4. 图片落盘，内存只留索引

`state.json` 只存文字和图片文件名（几 KB），PNG 在 `%APPDATA%\FloatNote\media`。
开 20 个窗口装 100 张图，内存不涨。启动时按需解码，并用 `Freeze()` 让位图可跨线程共享。

### 5. 事件驱动，零轮询

全局热键走 `RegisterHotKey` + `WM_HOTKEY`，剪贴板不做轮询。
空闲时 CPU 实测 **0.000%**（窗口隐藏状态）。

### 6. 失焦即释放输入框焦点

这是本项目**最重要的一处 CPU 优化**，实测差别很大：

WPF 里只要 `TextBox` 持有逻辑焦点，光标就以约 530 ms 周期闪烁并触发重绘。
多个便签常开时，这些看不见的重绘会持续吃 0.5%–1.5% CPU。

改成"激活时聚焦、失焦时把焦点转交给根 Grid"后，实测降到 **0.000%**。

## 三、实测数据

测试环境：Windows 11 (10.0.26200)、16 逻辑核、3200×2000 @200% 缩放、.NET 10。
以下全部为本机实测，非估算。测量时程序完全静置（无鼠标/键盘操作）。

### CPU

| 场景 | CPU（单核占比） | 折合整机（16 核） |
|---|---|---|
| 1 个空便签，静置 | **0.00%** | 0.000% |
| 4 个便签 + 20 条目 + 10 张 1600×1000 图 | 0.39% | 0.024% |

空闲时为零，因为全程事件驱动：热键走 `WM_HOTKEY`，不轮询剪贴板，没有动画定时器。
唯一会持续产生开销的是**输入框光标闪烁**，所以窗口失焦时会主动释放焦点（见第二节第 6 条）。

### 内存

| 场景 | Working Set | Private Bytes |
|---|---|---|
| 空 WPF 窗口（框架基线，对照） | 114 MB | 77 MB |
| 空 WinForms 窗口（对照） | 31 MB | 7 MB |
| 1 个空便签 | 141 MB | 103 MB |
| 4 窗 + 20 条目 + 10 图 | 199 MB | 140 MB |
| 9 个空便签（早期版本实测） | 152 MB | 111 MB |

**怎么读这组数字：**

- 基线约 141 MB，其中 **114 MB 是 WPF 框架本身**（空窗口就占这么多），
  应用自身逻辑只占约 27 MB。这是 WPF 的固有代价，不是实现问题。
- 多开窗口的边际成本很低：2 → 9 个窗口，总内存只涨约 30 MB。
  因为所有窗口共享同一个 CLR 和渲染线程，第 2 个窗口的增量只有几 MB。
- 内容多了会涨。10 张 1600×1000 截图按缩略图尺寸（640px 宽）解码，
  约每张 2–3 MB。

### GPU 显存

| 场景 | Dedicated VRAM |
|---|---|
| 1 个便签（半透明置顶） | **14.6 MB** |

半透明分层窗口必然占用一部分显存做合成，这是"真透明 + 始终置顶"的代价。

### 磁盘

| 项目 | 大小 |
|---|---|
| 程序本体 `FloatNote.exe` | **301 KB**（单文件） |
| 数据目录 `%APPDATA%\FloatNote` | 75 KB（4 窗 20 条目场景） |
| 　其中截图 PNG | 72 KB（10 张 1600×1000） |
| 　其中 `state.json` | 2.9 KB |

依赖框架发布，运行时由系统共享，不重复打包 .NET。这是体积能压到 301 KB 的原因。

### 一句话总结

**CPU 空闲为 0；单窗口约 141 MB（其中 114 MB 是 WPF 框架）；多开几乎不涨；
显存 15 MB；程序 301 KB。**

如果内存比视觉质量更重要，WinForms 版本基线约 31 MB，
但圆角、阴影、字体渲染都会明显变糙。这个取舍写在这里供参考。

## 四、功能与快捷键

| 快捷键 | 作用 |
|---|---|
| `Ctrl+Shift+S` | 框选截图 → 投进当前便签 |
| `Ctrl+Shift+A` | 全屏截图 → 投进当前便签 |
| `Ctrl+Shift+N` | 新建便签窗口 |
| `Ctrl+Shift+H` | 显示 / 隐藏全部 |
| `Enter` | 保存速记（`Shift+Enter` 换行） |
| `Ctrl+V` | 粘贴文字或图片 |
| `Ctrl+W` | 隐藏当前窗口（内容保留） |

### 标题栏按钮（从左到右）

`+` 新建便签 · `置顶` 切换 TopMost · `相机` 截图 · `粘贴` · `…` 更多 · `˅` 收起 · `×` 关闭

其中 `+` 是新建窗口的最快入口（也可用 `Ctrl+Shift+N`），
放在标题栏最左侧，不用去翻托盘菜单。

### 内容操作

- **点击图片** → 应用内放大查看
  - **拖窗口边缘/角落** → 调整视图大小
  - 双击标题栏 → 最大化 / 还原
  - `Ctrl+滚轮` → 缩放图片内容（与窗口大小独立）
  - 拖动图片 → 平移查看局部
  - `Ctrl+S` 另存 · `Esc` 关闭
- **双击标题栏** → 收起 / 展开
- **双击标题文字** → 重命名
- **拖动标题栏** → 移动窗口（`WindowChrome` 原生拖动，GPU 合成）
- **拖边缘** → 调整大小

> 图片放大用的是应用内窗口，不是系统「照片」应用。
> 原因：系统照片冷启动要 3–8 秒，且依赖 `.png` 文件关联，体验不可控。

### 关闭 vs 隐藏（重要）

| 操作 | 结果 |
|---|---|
| 点 `×` 关闭 | **丢弃该窗口全部内容（文字 + 截图文件），有确认弹窗** |
| `Ctrl+W` 或「收起」 | 仅隐藏，内容保留，可再唤出 |

「关闭即清空」是为了省存储而做的设计选择。误点关闭会有确认框兜底。

## 五、打开与关闭

### 打开

任选一种：

1. 双击 `FloatNote.exe`
2. 开始菜单 → 搜索 `FloatNote`（若创建了快捷方式）
3. 开机自启后自动出现（见下）

**如果双击后没看到窗口**：程序已在运行，它会自动把窗口唤到前台。
若仍找不到，看屏幕**右侧竖排区域**——新窗口默认出现在那里。

### 关闭

| 方式 | 说明 |
|---|---|
| 托盘图标右键 → 「退出 FloatNote」 | 最彻底，结束进程 |
| 便签标题栏「…」菜单 → 「退出 FloatNote」 | 同上（托盘图标可能被 Win11 折叠，用这个更直接） |
| 任务管理器 → 结束 `FloatNote` | 兜底 |

⚠️ 退出会清空所有便签内容（这是为节省存储而做的设计选择）。

### 开机自启

已注册在注册表：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
  FloatNote = "C:\...\FloatNote.exe" --silent
```

`--silent` 表示**启动时不抢焦点**，但窗口依然可见（显示在屏幕右侧）。

开关方式：托盘右键菜单 → 勾选/取消「开机自动启动」。

自启后会看到托盘气泡提示「FloatNote 已启动，便签在屏幕右侧」。

## 六、常驻与找回窗口

程序是**单实例常驻**：只有一个进程，关掉窗口不等于退出程序。

**找不到窗口时，按顺序试：**

1. 再双击一次 `FloatNote.exe` → 会把已有窗口唤到前台
2. `Ctrl+Shift+H` → 显示全部
3. 托盘图标左键 → 显示/隐藏
4. 托盘右键 → 「显示全部」

### 为什么之前会「看不见」

之前有两个真实缺陷，已修复：

1. **第二次双击 exe 时静默退出**——没有新窗口，也没有任何提示，看起来像"没反应"。
   现在改成通过命名管道唤醒已有实例。
2. **`--silent` 自启时窗口是隐藏的**——开机后桌面什么都没有，只剩一个托盘点。
   现在自启后窗口可见（只是不抢焦点）。

另外，「窗口不在任务栏」是有意设计（便签属于工具窗），所以切到别的程序后
只能靠 hotkey / 托盘 / 重开 exe 找回，不会出现在 Alt+Tab 里。

```bash
dotnet build -c Release

```

发布单文件：

```bash
dotnet publish -c Release -r win-x64 --self-contained false \
  -p:PublishSingleFile=true -o ./dist
```

`--self-contained true`，体积会增到约 70 MB，但免安装。

## 九、已知边界

1. **内存基线偏高是 WPF 的固有代价。** 如果"内存"是第一优先级，WinForms 版本
   基线约 31 MB，代价是圆角/阴影/字体渲染质量明显下降。取舍取决于哪一项更被看重。
2. **窗口不出现在任务栏、Alt+Tab 里**（便签按工具窗处理）。切走后靠
   `Ctrl+Shift+H`、托盘、或再双击一次 exe 找回。
3. **多显示器不同缩放**：截图坐标全程用物理像素（`GetCursorPos` + `GetSystemMetrics`），
   已规避 DPI 换算偏移；但极端混合缩放组合仍建议实测确认。
4. **退出即清空**：为省存储，关闭窗口 / 退出程序都会删除内容与截图文件，
   只有确认弹窗兜底，**没有回收站**。重要内容请先 `Ctrl+S` 另存。
5. **截图时其他便签会短暂隐藏**，截完立即恢复——否则会截到自己的窗口。
6. **无加密**：`state.json` 和截图是明文。若存放敏感信息，建议后续加 DPAPI。
7. **应用内看图**：不支持 GIF 动图播放与 EXIF 方向自动纠正以外的格式特性，
   只做等比显示与缩放。

## 十、变更记录（本轮修复）

| 问题 | 原因 | 处理 |
|---|---|---|
| 双击 exe「没反应」 | 单实例静默退出，无任何提示 | 命名管道唤醒已有实例并置前 |
| 开机后看不见窗口 | `--silent` 时执行了 `Hide()` | 改为可见但不抢焦点 |
| 点击图片无响应 | 命令绑定注册在 `App`（不在可视树），路由找不到处理者 | 改注册到 `NoteWindow` |
| 图片放大后四周白块/灰条 | `ScrollViewer` 滚动条交汇角与 `Button` 默认模板底色 | 改自绘 `Border` + 变换；按钮换纯 Border 模板 |
| 缩略图占满整窗、时间戳被挤出 | 未限高 | 限 `MaxHeight=150` DIP |
| 标题栏按钮空心方块 | 图标字体回退 | 显式指定 `Segoe Fluent Icons` 并保留 MDL2 兜底 |
| 窗口尺寸被改小、位置跑到左上角 | JSON 缺失字段反序列化为 `0` 而非 `NaN`；`ApplyCollapsed(false)` 在构造期无条件覆盖 `Height` | 位置判"是否落在屏幕内"；展开分支仅在 `_restoreHeight>0` 时还原 |
| 尺寸被写成错误值 | `SizeChanged` 在首帧布局期触发，把未完成的 `ActualHeight` 写回 | 加 `_boundsReady` 门闩，`Loaded` 之后才允许持久化 |
| **点截图按钮白屏卡死** | 全屏 `AllowsTransparency=True` 分层窗口（3200×2000 表面，软件合成）+ `ShowDialog` 模态消息循环死锁 | 改为「先 GDI 抓屏 → 在静态图上框选」，`Show()` + `TaskCompletionSource` 异步等待，彻底去掉模态循环 |
| 出了异常直接消失、无从排查 | 无全局异常处理 | 加 `crash.log`（异常栈）+ `trace.log`（关键步骤追踪） |
| **透明度只变暗、不真透明** | `AllowsTransparency=false` 时 WPF 的 `Window.Opacity` 只是把内容按比例压暗（实测 255→166），不做 alpha 合成；改用 `WS_EX_LAYERED` 又被 WPF 的 HwndSource 重置 | 改为 `AllowsTransparency=true`，圆角/拖动手势自绘。实测反解 α 与配置一致（0.65→0.650） |
| 加 `AllowsTransparency` 后窗口被压成一条标题栏 | 它与 `WindowChrome` 互斥：分层窗口没有系统非客户区 | 移除 `WindowChrome`，拖动用 `WM_NCLBUTTONDOWN`、缩放用自绘热区 |
| 自绘热区导致整窗变空白 | `root.Child = null` 后把根部整个替换，内层内容未挂回 | 只取出内层内容再放回新宿主 |
| 收起态高度被持久化成 34 | `PersistBounds` 未区分收起态 | 收起时跳过持久化，并在展开时对异常高度兜底 |
